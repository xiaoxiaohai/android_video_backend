# 解析探索总结（2026-02-27）

## 1. 当前核心诉求

你的目标是：

1. 复现并接近 `cine` app 的播放解析效果（m3u8 + 字幕）。
2. 重点验证为何上游会返回 `Referer: https://streameeeeee.site/`，而我们常拿到 `https://videostr.net/`。
3. 希望在可控前提下提升命中 `streameeeeee` 的概率。
4. 用可批量、可复现的实验方式（多入口域名、多 IP、多策略）定位差异原因。

---

## 2. 已确认的事实

## 2.1 App 侧逻辑（反编译结论）

1. 客户端播放主流程以 `channels` 里的线路 URL 为主，不依赖外层 `MovieEntity.url`。
2. 客户端调用上游 `pl/ad` 做播放解析，再用结果中的 `files`（含 headers）播放。
3. 客户端还会拿 `caption` 数据做字幕展示/选择。

补充：
- `MovieEntity.url` 在主播放流程中不是核心字段，更多是展示/其他用途。

## 2.2 “同一 watchUrl，不同解析结果”确实存在

对同一链接：

`https://f2moviesz.uk/watch-movie/watch-the-wrecking-crew-movies-free-hd-142383.13002473`

实测出现差异：

1. 上游 `pl/ad`：
   - `refererHost = streameeeeee.site`
   - `fileHost = silvercloud9.pro`
   - `captionCount = 127`
2. 本地 resolver：
   - `providerHost = videostr.net`
   - `refererHost = videostr.net`
   - `fileHost = skyember44.online`
   - `captionCount = 37`

这说明上游服务端有额外调度/处理，不是简单透传 provider 链接。

## 2.3 `streameeeeee` 不是固定可替代域名

1. 部分样本链路里 provider 明确是 `videostr.net`。
2. 对同一个 `sourceId`，强行切到 `streameeeeee.site` 不一定能成功（可能拿不到有效 key 或返回异常）。
3. 结论：不能假设 `videostr` 与 `streameeeeee` 完全互通。

## 2.4 入口域名会影响结果，但不是唯一因素

对 `.uk` / `.la` 分别做了入口对照实验：

1. 有时 `.uk` 的 `episode/sources` 字段不稳定（历史上出现过空 link）。
2. `.la` 更稳定返回 provider，但仍可能是 `videostr.net`。
3. provider 分配受多因素影响：域名入口、会话、出口 IP、风控状态、时段调度。

## 3. 代码与工具现状

## 3.1 本地 resolver 相关

已在本地测试链路中加强：

1. `megacloud` 提取逻辑支持“优先 embed-origin，失败回退 videostr”。
2. provider 采用插件化结构（`f2movies` / `flixhq` / `novhop`）。
3. 保留 `file + headers` 联动输出，避免“只存 m3u8 导致 403”。

## 3.2 新增实验脚本

1. `scripts/explore_streameeeeee.mjs`
   - 作用：批量探索 provider 命中情况。

   - 作用：同一 URL 对比上游 `pl/ad` 与本地 resolver 差异。
   - 输出：file host / referer host / caption count / language diff。
   - npm 命令：`npm run compare:resolver`

输出目录：

- `backend/output/streameeeeee-explore/`
- `backend/output/resolver-compare/`

## 5. 当前判断（阶段性）

1. 上游 `pl/ad` 后端不是“纯 provider 直解”，而是有二次策略（可能包括源池、headers 归一化、字幕聚合、风控兼容）。
2. 我们想稳定命中 `streameeeeee`，不能靠单点硬编码，必须用实验矩阵找触发条件。
3. 业务上应优先保证可播率，再追求特定 provider 命中率。

## 6. 下一步建议（可直接执行）

1. 用你的多国家 IP 跑 `explore:streameeeeee`（同一 URL、同一时间窗）：
   - 对比各地区 `episodeProviderHost` 命中分布。
2. 对命中 `streameeeeee` 的样本再跑 `compare:resolver`：
   - 看是否仍存在字幕数量与 file host 差异。
3. 根据数据决定是否引入“策略层”：
   - 优先 `streameeeeee`（仅在可得且稳定时）
   - 失败快速回退 `provider-origin`
   - 保持 `file + headers` 一起输出和缓存。

## 7. 一句话结论

当前不是“代码写死 videostr”的单点问题，而是上游调度与会话风控共同作用导致的 provider 分流问题；解决路径应是数据化探索 + 策略化回退，而不是强行固定某个域名。
